# Task 001 — 宇宙电台：第一条可收听节目

## 目标

在现有 esp32 仓库下新建 radio/，做一个能真实生成稿件、合成语音、保存并在 Web 重听的最小广播原型。重点是验证内容是否有趣，而不是先完成整台收音机。严格分步执行，每个检查点完成后汇报并等待用户确认，不要一次完成全部任务。

## 已确认的产品边界

- 核心体验：拧旋钮接收到五花八门的宇宙广播，新闻、聊天、音乐及语言、音效等表现可以组合；内容要能理解，不是随机噪音。
- 不要求固定世界观、严格频道时间线或持续 24 小时生成。将来可以增加这些能力，但现在不实现。
- 内容生产与播放解耦，生成跟不上时用默认音频填充。V0.1 先验证生成与收听，不实现完整库存调度。
- 永久排除登录/账号、网易云等现成音乐平台接入、语音助手、闹钟；不需要麦克风。
- 后续实体设备使用已有 ESP32-S3 N16R8、EC11、ST7735 TFT、MAX98357A 和喇叭。此任务不改固件，不购买硬件。

## 技术与仓库约束

- 仓库：mayloveless/esp32，直接使用现有仓库，不新建 Git 仓库。
- 根目录已有 drum/ 与 drum-web/；不得修改或重构鼓机。
- radio/ 使用单个 Next.js + TypeScript 项目、pnpm，不拆独立前后端或微服务。
- 不引入通用 Agent 框架、Redis、独立队列服务、复杂 ORM、账号系统或不必要的抽象。
- 数据使用现有 Supabase 项目 supabase-lottery，project ref：lhiojnqooreavzmkrzji；不创建新项目。仅新增 radio_ 前缀业务对象，不碰其他项目的数据和权限。
- 数据库/Storage 可由已连接的 Supabase 插件直接操作；若 Codex 无法访问连接，先汇报，不要冒充已执行，也不要要求用户重建项目。
- 实际生成的音频与秘密不提交 Git；提交 lockfile、配置模板、必要的迁移 SQL 和简短 README。

## 第一阶段：项目初始化（先执行，完成后暂停）

1. 读取仓库根目录、现有规则和 radio/ 是否已存在，确认没有未提交修改会被覆盖。
2. 在 radio/ 初始化最小 Next.js App Router + TypeScript + pnpm 项目，保留正常的 lint/typecheck/build 脚本。不要建立额外 workspace 或 packages。
3. 增加一页简洁的电台实验台：节目形式选择（新闻/聊天）、语言与风格的基础输入、生成入口、内容预览、音频播放器和节目列表区域。此阶段允许 UI 是空状态，不伪造生成成功。
4. 按职责保留少量服务端模块：content、renderer、program、lib。不要为尚未实现的业务创建空类、Repository/Service/Controller 三件套或复杂 DI。
5. 增加 .env.example、README 与合理的 gitignore。先给出环境变量名称，不填写真实密钥。此阶段不得调用付费 AI。
6. 执行可用的 lint、typecheck、build，汇报结果和修改文件。完成后暂停，等待用户 review。

## 第二阶段：最小数据与音频资源（确认后执行）

使用已确认的 Supabase 项目。先检查当前 schema、迁移和 bucket，不重复创建现有资源。数据库结构由 ChatGPT/Supabase 插件执行或经用户确认后由 Codex 执行；最终在仓库保留可复现的迁移 SQL，不要在多个执行入口重复应用。

第一版只需 radio_programs 一张表：UUID id、status（queued/generating/ready/failed）、format、title、recipe JSONB、content JSONB、captions JSONB、audio_path、duration_ms、error、created_at、updated_at。字段可按真实实现微调，JSONB 必须有基本类型校验。不要提前建世界、角色、频道时间线或任务系统的多张表。

Storage 使用独立 radio-audio bucket，保存生成音频，数据库保存对象路径而不是临时签名 URL。默认私有，服务端生成限时读取地址。不对 anon 开放写入，不把 secret/service_role key 放入浏览器或 NEXT_PUBLIC_ 环境变量。所有生成、修改与存储操作经过服务端；本地开发也应有默认仅本机可用的保护，未来部署前再明确访问控制。

验证数据库与 bucket 可读取，必要时使用可清理的测试数据，不能碰其他业务表。不要因为复用公共项目就关闭其他表的 RLS。

## 第三阶段：真实内容与 TTS（确认后执行）

先做一条有实际内容的端到端链路：

Web 输入节目形式/主题/语言/风格 → 服务端生成有意义的中文语义稿件 → TTS → 上传音频 → 保存 Program → Web 播放并展示稿件。

- 使用用户已有且实际可调用的 AI 服务；第一版优先用一个文本生成供应商和一个 TTS 供应商。具体模型、SDK 与音频格式实施前按当前官方文档确认，模型名通过环境变量配置。不得编造 API 返回值或假称完成真实生成。
- 若使用 OpenAI，密钥仅在服务端，采用官方 SDK；提供必要的模型环境变量及 .env.example，不提交密钥。无法读取用户实际密钥时由用户本地配置，不要求把密钥发到聊天。
- 内容与表现分离：先保留可理解的语义稿件，之后才进行语言/TTS/音效渲染。新闻和聊天使用统一的节目资源格式，不为每种语言建立独立业务系统。
- 文本生成输出结构化数据并进行运行时校验；限制单次生成长度、并发和超时。失败应记录失败状态和可诊断错误，不产生假 ready 记录。
- 第一版可以先合成整段语音，字幕使用整段或按句分段；不伪造精确逐字时间戳。
- 对真实知识不得编造来源；如果没有检索或可验证素材，明确采用虚构广播内容或用户提供的事实素材，不把 AI 生成的虚构新闻标成现实新闻。
- Web 显示生成进度、错误、稿件、音频及历史记录；重新打开页面仍可播放已保存节目。
- 不自动批量调用付费 API，不做无限循环生成，不做真实时间线、AI 作曲、外星语生成或 ESP32 接入。这些留到下一任务。

## 完成标准与汇报

最终能够在本地运行 Next.js，生成一段真实语音，保存到既有 Supabase，刷新页面后仍能看到并播放。缺少可用 AI 密钥时，应明确说明阻塞点，完成不需密钥的可验证部分，不用 mock 冒充真实完成。

每个阶段结束只汇报：实际修改文件、关键实现决策、运行的命令及结果、尚未完成的内容。用户确认后再进入下一阶段。不要自行提交未经 review 的大批量代码，不要修改鼓机，不要扩展产品范围。
