# 连续播放流量诊断（2026-10-07）

用户反馈节目“播一帧停一下”、音量小。固件起点为 011B 播放路径，011C 探针保持撤回。此轮增加默认关闭的 `RADIO_PLAYBACK_FLOW` 被动统计，每三秒由主循环记录输入缓冲、库播放时钟、raw PCM 提交帧数和最大提交间隔；回调不打印、不分配、不调用网络或 Audio 控制函数。捕获器只保留安全字段，不保存 signed URL 路径或 query。

## 观察

- 初始统计固件的启动连接遇到既有 TCP 失败，不能用于流畅度判定；用户后续实体选台后采到了 61 个三秒窗口，PCM 提交比率中位数约为实时需求的 0.277，见 [初始统计样本](playback-flow-baseline.txt)。
- 应用 I2S 输出队列补丁并烧录后，云端 CHAT 正常开始播放、Range 206 与 offset 应用通过；首 60 个三秒窗口的提交比率中位数约 0.341，25 个缓冲快照为空，最大 PCM 间隔 1477ms。这不是相同节目/相同条件的严格 A/B，不能据此计算补丁改善百分比。确认的是修复后仍严重供给不足，见 [云端样本](playback-flow-cloud.txt)。
- 临时局域网服务提供自行合成的 32kHz mono 16-bit WAV，10 分钟、400Hz 低幅测试音；同一产品固件、同一个 Audio、同一 I2S 与 MAX98357A，仅测试输入改为局域网 HTTP。未播放真实节目文件；正常程序库存没有 completed。Range framing 用独立请求验证了 206、完整有限 8192-byte 响应及 WAV 头。
- 稳态局域网每 3000ms 提交 96000 PCM 帧，输入缓冲保持 655350 bytes，PCM 最大间隔约 11–21ms，库时间与墙钟同步推进，见 [局域网样本](playback-flow-local.txt)。首个窗口包含初始化，需排除。

## 结论与限制

同格式 WAV 在数据充足时可以持续解码输出。当前主要卡顿与云端 HTTPS 流输入不足一致，不能用 I2S 队列补丁声称已经解决流畅度；也不能归因于接线或仅凭本次实验断定路由器/外网故障。局域网为 HTTP，云端为 HTTPS，客户端 TLS、TCP 接收窗口、远端与链路时延仍需进一步区分；没有更改系统网络库、路由器、服务端格式或产品传输架构。

当前音频格式每秒需要 64000 bytes，即 512 kbit/s。观察到的 PCM 持续供给约为这一要求的三分之一。增加起播缓冲只能推迟断粮；当长期速度仍不足时不能保证无限持续播放。可选后续方案是压缩音频、局域网中转或接受明显更长预缓冲，等待用户对方案的偏好。

PCM 帧数是库回调的提交量，不是麦克风/I2S 实际完成计数；发生超时重试或部分写入时可能重复计入待发送片段。对照窗口无致命错误。`loopMaxMs` 只测 Audio.loop，不包含主循环其他工作；`dmaEvents` 是 ISR 事件累计数，不表示驱动可写槽数量。

临时测试输入已从产品源码移除，默认仍为 signed URL 流式播放、fast 开关默认关闭；本机验收构建沿用显式 fast=1 / 8192，flow=1。当时音量 18 的候选版编译通过（Flash 2,413,279 bytes / 76%，静态 RAM 70,356 bytes / 21%），烧录写入校验通过。最终启动 CHAT 在 9 秒 offset 完成 Range 206 与位置 576044 应用，3814ms 产生首个网络 PCM，prefetch 正常；录音/用户听感尚未确认音量改善，云端持续流畅度仍未通过。临时局域网服务已关闭，测试固件已替换为节目固件。最终轻微日志命名与音量变更后，playback 和 controls 两组回归再通过。

## 破音反馈后的回退

用户报告“全是破音”，撤回输出队列与音量两项实验。先烧入私有保存的 011B/8192 原始已验收 binary（SHA-256 `9b32d1695037b46fddcdd4b9e80407b53dd2d3c61c37cbef22a344c38f56bb06`），写入校验通过。这份早期 binary 与当前带 failure latch 修复的 HEAD 有版本差异。

恢复后串口显示 MUSIC 接入 11 秒 offset、首个 PCM 2975ms，正常自然 EOF 与 completed 成功；之后实体旋钮命中预取 ALIEN，但 fast 和 legacy 都在 TCP connect 阶段失败（errno 113），进入 SIGNAL LOST。用户此时反馈无声。因此不能把首次 PCM/EOF 记录作为当前扬声器已恢复的确认。

## 原输出 + 本机缓存的真实节目验证

两次恢复云端取流后，仍发生 fast/legacy TCP errno 113，保持 SIGNAL LOST；再次提高音量或修改 I2S 无法修复这个连接失败。新增**默认关闭**的本机开发缓存，当前本机 `.env.local` 临时选择 `local-cache`，音频 URL origin 为已有开发服务的 LAN 地址。源码、已安装库和板上固件仍为原 I2S 输出、音量 15；原 WAV、节目 offset、字幕与自然 completed 保持不变。没有启用 MP3 副本，没有调用 AI 重新生成此轮测试音频。

设备专用缓存 URL 以现有服务端 Device key 作 HMAC 签名，但不包含 key；签名绑定不可变源 object 路径版本、文件名和 15 分钟过期时间。未经签名/过期拒绝；Range 返回原字节及完整文件总长。电脑完整取得音频后才签发地址。私有音频不作为公开静态文件。最多 64MiB 内存缓存、单条 32MiB、两个并行载入、LRU 淘汰、同一 pending 去重；服务重启或淘汰导致旧 URL 404，需要实体重新调台。该模式需要开发机持续运行，仍属于可信 LAN 上已有 HTTP Device API 的开发方式；关闭环境开关恢复云端直连。

缓存 HTTP 集成验证通过：未签名 403，8192-byte initial 206 和 seek 有限 Range 都正确，见 [HTTP 校验](playback-cache-http.json)。预热少量当前现成库存后，设备重启正常从本机地址接入一条 NEWS WAV，稳态每 3000ms 96000 PCM 帧，maxGap 9–15ms，输入保持满载直到文件末尾；字幕依库的真实时间推进，自然 completed 成功，见 [真实节目串口](playback-cache-trace.txt)。这一轮没有退回失败的输出队列候选，也没有提高音量。用户随后确认原先“播一帧停一下”的断续感已消失，但仍有偶发爆音。连续播放听感已改善；爆音原因尚未定位，不能仅凭提交帧统计排除输出、供电或接触问题。

签名/过期/对象绑定、初始/seek/非法 Range、pending 去重、失败重试与 LRU 单元测试通过；Checkpoint B 全部 134 项通过，类型检查与目标文件 lint 通过。电脑同曲 WAV/MP3 对照准备已完成，但 codec prototype 未烧录，临时 HTTPS 服务已经关闭。当前正常换台使用缓存模式，用户已确认断续感消失；偶发爆音仍待定位，不能标记整体音质验收通过。

首条 NEWS 的缓存准备及 manifest 请求约 5.75s；收到 manifest 后到首个 PCM 为 226ms，目标 Range 25ms。226ms 不包含首次电脑下载与 Device tune 请求时间，不能作为首次启动的全部耗时。首次窗口含初始化，93952 帧；后续稳定为 96000 帧。后台下一条 prefetch 准备 4310ms，没有打断当前音频。此次缓存验证使用的固件自然结束后依原有行为保持 NO SIGNAL，等待实体旋钮调台。当时未添加自动续播；用户随后要求补上，该行为由 [自动续播改动](automatic-continuation.md) 覆盖。
